# Skill: Markdown文档格式规范

## 技能说明与触发

本技能定义统一的 Markdown 文档格式规范，涵盖**标题层级与编号**、**列表样式**、**中英排版**、**函数与源码引用格式**及**文档结构**。凡用户要求**创建** Markdown 文档（如"生成一份……文档"、"帮我把这些内容写成 md"）或**修改**已有文档（追加内容、增删调整标题、优化结构）时，必须遵循以下规则。非标题内容（段落、表格、代码块等）不受第 1、5 节标题规则约束，但须遵守第 2～4、6、7 节规范（列表、排版、加粗、函数、源码引用），其余按普通 Markdown 语法处理。

## 强制格式规范

### 1. 标题编号格式

- 禁止一级标题 `#`。
- 二级 `##`：中文数字 + 顿号，全文顺序递增。示例：`## 一、 项目背景`。
- 三级 `###`：阿拉伯数字 + 点号，编号在每个二级标题下独立从 `1.` 开始。示例：`### 1. 功能概述`。
- 四级 `####`：`<三级编号>.<四级序号>`。示例：`#### 1.1 子功能A`。
- 五级 `#####`：`<三级编号>.<四级编号>.<五级序号>`。示例：`##### 1.1.1 详细说明`。
- 六级 `######`：`<三级编号>.<四级编号>.<五级序号>.<六级序号>`。示例：`###### 1.1.1.1 补充说明`。
- 依此类推，每深一级在末尾追加一段序号，各段用点分隔；各层级编号均在其父标题下独立递增，编号与文本之间必须有一个空格。所有层级**必须带编号**，禁止无编号的裸标题（如 `##### 要点`、`##### （1）xxx`）。

### 2. 列表规范

- 无序列表必须用 `-`，禁止 `*` 或 `+`；列表项内容与标记之间一个空格；嵌套列表缩进两个空格。
- 有序列表禁止使用 Markdown 的 `1.` `2.` `3.` 语法，必须用全角括号数字：（1）（2）（3）……编号手工维护，增删项后重新编号。
- （N）编号项每项独占一行，**项与项之间必须空一行**，否则渲染时会合并成同一段落。

### 3. 中英排版规范

- 英文单词、数字、英文标点与中文字符之间前后各加一个空格。示例：`使用 React 框架`、`版本号为 2.5.0`。
- 纯英文段落或代码块内不受此限；Markdown 标记（`#`、`` ` ``、`**` 等）不计入判断。

### 4. 整行加粗格式规范

- 整行内容全部为加粗、且加粗内容不超过 10 个汉字时，外面加中文方括号【】。正确示例：`【**注意**】`。
- 不满足条件时不加【】，保持原样即可，如 `**注意**：请仔细阅读`（行内有其他文本）、超过 10 个汉字的整行加粗。

### 5. 标题层级使用原则（强制）

通篇二级标题平铺是最常见的结构性错误：板块内部的细节被提升为二级标题，文档只剩"清单感"。必须按本节规划层级。

#### 5.1 层级语义定位

把文档当成一本书：二级是"章"，三级是"节"，四级是"小节"，五级、六级是"条目"。动笔前先问"这本书分几章"，而不是"我有哪些话题"。

| 层级 | 定位 | 自查问题 |
| ---- | ---- | -------- |
| `##` 二级 | 文档的一级逻辑板块（章） | 删掉它，文档骨架是否缺一块？只有"是"才配当二级 |
| `###` 三级 | 板块下可独立成段的主题（节） | 它是板块内部的一个独立主题吗？ |
| `####` 四级 | 主题下的细分点（小节） | 它是主题内部的子方面、子步骤或子情况吗？ |
| `#####` 五级 | 细分点下的具体条目 | 它是细分点下的条目、示例或细则吗？ |
| `######` 六级 | 条目内部的再展开 | 极少使用，确有必要才用 |

内容 A 是内容 B 的组成部分或子集时，A 的层级必须低于 B；只有同范畴、同抽象层级且无包含关系的内容才允许同级并列。

#### 5.2 量化硬约束

- 二级标题必须为 **3～7 个**，**达到 8 个即必须重新归组**——同属一个宏观板块的二级标题合并为一个，原内容依次降为三级、四级。例外：内容很少的短文档（一两个板块即可说清、下级标题也不多）可少于 3 个二级标题，不受下限约束。
- 归组建树后二级标题仍达 8 个，说明内容体量已超出单篇文档的承载范围，应考虑**按板块边界拆分为多篇文档**（每篇自成一个完整主题，篇间用相对链接互相引用），而不是硬塞成一篇。
- 子功能、子步骤、子情况、具体条目等细节**禁止提升为二级标题**，必须在对应三级或四级标题下展开。
- 拿不准层级时，默认**降一级挂到现有父标题下**，而不是新增同级标题。
- 同一父标题下子标题超过 7 个时，检查是否遗漏了一层中间分组。

#### 5.3 写前规划四步法（创建新文档或调整结构时必须执行）

（1）**列内容点**：全部内容点列成清单，此时不关心层级。

（2）**归组建树**：按"板块 → 主题 → 细分点 → 条目"归组建树，板块控制在 3～7 个（短文档例外见 5.2）。

（3）**定层级出大纲**：翻译成带编号的标题大纲，逐个检查二级标题能否通过 5.1 的"章"自查。

（4）**按大纲生成正文**：生成中不得临时把四级内容提升为二级标题。

#### 5.4 反模式示例

平铺式（**错误**）：

```markdown
## 一、 项目背景
## 二、 硬件选型
## 三、 软件架构
## 四、 通信协议
## 五、 协议帧格式
## 六、 协议交互流程
## 七、 调试方法
## 八、 测试用例
## 九、 常见问题
```

归组式（**正确**）——"通信协议/帧格式/交互流程"同属方案设计，"调试/测试/常见问题"同属验证维护，归组后细节降级：

```markdown
## 一、 项目背景
## 二、 方案设计
### 1. 硬件选型
### 2. 软件架构
### 3. 通信协议
#### 3.1 协议帧格式
#### 3.2 协议交互流程
## 三、 验证与维护
### 1. 调试方法
### 2. 测试用例
### 3. 常见问题
```

#### 5.5 生成后自检（交付前必须执行）

统计全文各层级标题数量，出现以下任一情况必须重组后再交付：

- 二级标题达到 8 个（先重新归组；归组后仍超限，按 5.2 考虑拆分为多篇文档）；
- 二级标题不足 3 个且三级及以下标题超过 7 个（板块划分过粗、层级过深，应把可独立成板块的主题提升为二级标题）；
- 存在正文只有一两段或一个列表的"空壳"二级标题（应并入相邻章节或降级）；
- 存在伪并列：两个同级标题实际有包含关系，或能轻松起出一个共同的父标题名（说明该降级）。

### 6. 函数说明格式规范

介绍函数（C 函数、API 等）时的固定格式：

- 标题：`<编号> <函数名>()`，函数名后必须带空括号，层级按文档结构灵活选择。
- 标题后第一段说明用途并写明声明位置：`该函数在 \`<文件路径>\` 文件中声明：`，路径用反引号包裹。
- 随后给出标注语言的声明代码块。
- 详情依次用三个整行加粗引导行（格式见第 4 节）：【**函数作用**】；【**参数含义**】，用 `- \`参数名\`：说明` 逐个列出；【**返回值**】，有多种情况分别说明。

完整示例：

````markdown
#### 2.1 cdev_add()

字符设备添加所用到的函数为 `cdev_add()`，该函数在 `内核源码/include/linux/cdev.h` 文件中声明：

```c
int cdev_add(struct cdev *, dev_t, unsigned);
```

【**函数作用**】

该函数向内核注册一个 `struct cdev` 结构体

【**参数含义**】

- `p`：要添加的 `struct cdev` 类型的结构体
- `dev`：申请的字符设备号
- `count`：和该设备关联的设备编号的数量

【**返回值**】

添加成功返回 0，添加失败返回负数
````

### 7. 源码引用格式规范

- 引用源码的代码块，第一行用该语言的注释语法写明相对路径，如 `// drivers/char/mem.c`。
- 正文中的文件引用，按优先级判断：（1）用户已指定基础路径 → 用该路径构建超链接；（2）文档与被引用文件同仓库 → 用相对路径构建超链接；（3）均不满足 → 禁止超链接，仅用反引号包裹路径。
- 超链接格式：整文件 `[文本](路径)`、单行 `[文本](路径#L42)`、行区间 `[文本](路径#L42-L50)`。

示例：

````markdown
`memory_open()` 函数定义在 [`drivers/char/mem.c`](drivers/char/mem.c#L42) 中：

```c
// drivers/char/mem.c
static int memory_open(struct inode *inode, struct file *filp)
{
    // ...
}
```
````

## 行为规范

### 创建新文档

（1）先按 5.3 规划标题大纲，确认二级标题数量符合 5.2 的约束后再动笔。

（2）生成时自动应用第 1～4 节的全部格式规范。

（3）文档第一行必须添加 `<!-- more -->`，其后保留一个空行再接正文，不区分文档类型。

（4）交付前按 5.5 自检，不合格必须重组；然后在末尾添加：

   ```
   ---
   *本文档由 markdowncli 技能辅助生成*
   ```

### 修改已有文档

（1）先读全文，统计各级标题数量，判断是否存在平铺（二级达到 8 个）、空壳章节、伪并列。

（2）用户要求"优化/整理/重构结构"时，必须按 5.3 重新归组；内容体量确实过大、归组后二级标题仍超限的，建议用户拆分为多篇文档；仅局部修改时保持原结构，但发现平铺问题应主动提醒用户。

（3）新增/修改的标题沿用文档已有的编号风格（已有风格本身违反第 1 节的，按第（4）步修正）；插入、删除或调整层级后，重新编排受影响层级的全部编号（二级中文数字整体重排，下级编号在其父标题内独立重排），确保连续无断档。

（4）顺带修正违反第 1～3 节规范之处：`#` 一级标题降为 `##` 并纳入编号体系；`*`/`+` 列表统一为 `-`；`1.` 有序列表改为（1）编号；变更文本补齐中英文之间的空格。

（5）修改时不添加 `<!-- more -->`；完成后按 5.5 自检，并在末尾添加与创建文档相同的提醒信息。

## 示例

"写一份用户登录模块的技术设计文档"的标题大纲：

```markdown
<!-- more -->

## 一、 总体设计
### 1. 登录流程
#### 1.1 凭证校验
#### 1.2 会话管理
### 2. 安全机制
#### 2.1 密码加密
#### 2.2 验证码处理
## 二、 接口定义
### 1. 登录接口
#### 1.1 请求参数
##### 1.1.1 用户名规则
##### 1.1.2 密码规则
#### 1.2 响应格式
```

"在'安全机制'后插入三级标题'日志审计'"：定位 `### 2. 安全机制`，其后插入 `### 3. 日志审计` 并顺延同级编号；新增标题的子标题（如 `#### 3.1 操作记录`）在新父标题下从 `1.` 重新编号。其他二级标题作用域内的编号不受影响。
